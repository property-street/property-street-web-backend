# Chat Logic
## message types
- incoming_message
- read_message
## data structure
```json
{
    category: str, # chat
    recipient_id: int,
    sender_id: int,
    msg_type: str, # incoming_message||read_message
    status: str, # unsent||sent||delivered||read
    unix_timestamp_ms: int,
    fmt_msg_txt: str,
    db_id: int, 
    thread_id: int,
}
```
## cached chat hset structure
- key: chat_{min(sender_id, recipient_id)}{max(sender_id, recipient_id)}
- fields: chat_object, lazy_timestamp, offloaded, offloading

## handle_chat
### incoming message
<!-- case for when a message is sent -->
- The message is sent to the recipient. If it fails, the message is added to the pend pool of the recipient, sent whenever the user is re-connected.
- a timestamp is gotten after it's sent and used as the message's timestamp, the status is updated to delivered, and the hset `chat_{min(sender_id,recipient_id)}{max(sender_id,recipient_id)}` is retrieved or created. 
- The timestamp is used as the key in the chat_obj dictionary, in the chat_object field, the lazy_timestamp is set as current_timestamp+CHAT_LAZY_OFFLOAD_SCHEDULE
- then updated object is sent to the sender's ws. If the send fails, it's also added to the sender pend pool.
### read message
<!-- case for when a message is read -->
- The chat_obj's status is updated to read and sent to the sender's websocket. If sending failure occurs, a ConnectionError is raised and the message is added to the sender's pend pool.
- The cached_chat hset is lookup for and updated based on the modification on the chat_object status.

## offload mechanism
- lazy offload
- expiry
- celery beat
### lazy or expiry
<!--whatever is contained in the chat_object field, it means it's new or modified, regardles of the db_id attribute-->
- acquire the lock to ensure no offload process is actively running.
- get the chat_object, if it's non-existent, return the function else load em.
- move the chat objects to the offloading field of the hset to maintain integrity.
- get the thread id of the chat 
- loop over the `loaded_chat_object`, and categorize into data for creation and update. 
- If the create_data exists, it's flushed so the db_id and the thread_id can be gotten. For each of the flushed instance, its equivalent obj on the `loaded_chat_object` is updated with the db_id and thread_id
- If the update_data exists, the msg object is updated.
- the db session is committed.
- the offloaded field is updated, with the current `loaded_chat_object`, the offloading field is deleted and the lazy_timestamp is updated individually to avoid overwriting another process.
