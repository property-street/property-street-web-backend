# Chat Logic

## message types
- incoming_message
- read_message

## cached dialogue hset key
```bash
chat_{min(sender_id,recipient_id)}_{max(sender_id,recipient_id)}
```
### fields: 
- chat_object: '{}' 
- lazy_timestamp: int 
- offloaded: '{}'
- offloading: '{}' `<!--short lived-->`

## message structure
`<!--This is what the data structure might look like when a chat is sent to a client.-->`
```json
{
    category: chat, # chat
    recipient_id: int,
    sender_id: int,
    msg_type: str, # incoming_message||delivered_message||read_message
    status: str, # unsent||sent||delivered||read
    unix_timestamp_ms: int,
    fmt_msg_txt: str,
    db_id: int, 
    thread_id: int,
}
```


## handle_chat function
### incoming message
<!-- case for when a new message is sent -->
- A timestamp is gotten and used as the message's timestamp.
- The message is sent to the recipient. 
    - If it fails, the message chat key is added to the recipient's pend_pool `messages`; sent whenever the user is re-connected.
    - else the status is updated to delivered, and the hset `chat_{min(sender_id,recipient_id)}{max(sender_id,recipient_id)}` is retrieved or created. 
- In the cached-dialogue hset, the timestamp is used as a key in the `chat_object` field dictionary, the lazy_timestamp is set as `current_timestamp+CHAT_LAZY_OFFLOAD_SCHEDULE`
- the updated object is sent to the sender's ws. If the send fails, the dialogue hset's key is added to the sender's pend_pool.
### read message
<!-- case for when a message is read -->
- The chat_obj's status is updated to `read` and sent to the sender's websocket. 
    - If sending failure occurs, a ConnectionError is raised and the dialogue's hset key is added to the sender's pend pool.
- The chat hset is looked-up for and updated based on the modification on the chat_object status.

## offload mechanisms
- lazy offload
- expiry
- celery beat
### lazy or expiry
`<!--whatever is contained in the chat_object field indicates a new or modified object, regardless of the db_id attribute-->`
- acquire the lock to ensure no offload process is actively running.
- get the chat_object, if it's non-existent, return the function else json-load em.
- move the chat objects to the offloading field of the hset to maintain integrity.
- get the thread id of the ids involved in the dialogue
- loop over the `loaded_chat_object`, and categorize into data for creation and update. 
    - If the create_data exists, it's flushed so the db_id and the thread_id can be gotten. For each of the flushed instance, its equivalent obj on the `loaded_chat_object` is updated with the db_id and thread_id
    - If the update_data exists, the msg object is updated.
- the db session is committed.
- the offloaded field is updated, with the current `chat_object` data, the offloading field is deleted and the lazy_timestamp is updated.

## Methods
### dispatch pending chat
#### NB: message token in a user's pend pool are stored in the format `dialogue_key:timestamp`
- get the user pend pool key
- retreive the message field of the user pend pool hset; this fields holds a list of tokens.
- an empty `dialogue_keys` list is initialized 
- if messages exists
    - initialize and empty `msg_to_dispatch` list.
    - each token is split, the dialogue key is appended to `dialogue_keys`.
    - the `timestamp` is then used to retrieve the chat object from from the dialogue's key `chat_object` field and appended to `msg_to_dispatch`.
    - if `msg_to_dispatch` is non-empty, it's sent to the connected websocket.

- if `dialogue_keys` is non-empty
    - The list is looped over.
    - If the item's `lazy_timestamp` is still in the future, the loop is skipped.  
    - the key is split to get the `min_id`, `max_id`, then `offload_chat_data` function is called with these parameters 

### offload chat data
#### parameters: min_id, max_id, chat_lazy_offload_schedule, redis_client, db
- A `dialogue_key` is constructed from the `min_id` and `max_id`.
- A lock key is constructed from the earlier constructed key.
- A redis lock is acquired. if false is returned, the function is exited; means another offloading process is ongoing.
- The `chat_object` field content of `dialogue_key` is retrieved.
    - If the `chat_object` does not exist, release the initially acquired lock, and return the function
- Delete the `chat_object` field of the hset to avoid race conditions.
- A thread_id is either created or gotten from the `min_id` and `max_id`, two empty lists `update_data` and `create_data` are initialized, the `chat_obj` is loaded into `loaded_chat_obj`, and looped over.
    - If the object contains a `db_id` attribute means the data should be updated, so it's grouped in the `update_data` list; else `create_data`
- Objects in `create_data` are persisted in the database; objects in the `loaded_chat_obj` without `db_id` are given one with a `thread_id`.
- PObjects in the `update_data` are updated.
- The modified `loaded_chat_obj` is save to the dialogue's hset `offloaded` field. The `lazy_timestamp` field is also updated.
- If any failure gets encountered, the `chat_obj` is re-saved to the `chat_object` field of the `dialogue_key`
- In the finally block the lock is released.
